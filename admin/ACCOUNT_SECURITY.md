# Managed identity and account recovery procedures

Only the designated administrator provisions the first Owner through managed Supabase Auth, after verifying business authority outside the app. Use a15+character passphrase/secure handoff, retain the stable Auth ID, then run reviewed bootstrap.sql with approved opening stock. Never create a separate password database or publish an account directory. Managed Auth stores password hashes. Disable public signup, configure minimum15 and TOTP enrollment/verification (config.toml expresses the intended settings; hosted settings still need verification). No ordinary app recovery or public signup screen exists.

Owner MFA enrollment/recovery is an administrator-assisted managed Auth procedure outside ordinary navigation. Do not hardcode codes or mark a client boolean trusted. All app staff changes require an actual managed factor challenge/verify and checked active Owner/AAL2. GitHub/Supabase administrators also use MFA through their provider controls. Staff own-profile edits preserve Auth IDs and cannot change roles/active status or others' profiles.

Functions configuration uses handler-managed authentication. username-login must accept pre-login requests, validates exact username/password schema, rate-limits HMAC buckets, resolves aliases through service-only SQL, authenticates through managed Auth and rechecks current active profile. staff-admin validates the bearer at managed Auth /user and calls database functions with the caller token; active Owner/AAL2 is authoritative. Gateway verify_jwt=false does NOT remove these checks; it avoids relying on the gateway's legacy JWT-key assumptions. Never replace handler/server verification with decoded unverified claims or client metadata. Local CLI HTTP defaults are not accepted by Android; use an isolated HTTPS-configured development stack/test CA. Production uses provider HTTPS. No TLS-verification bypass is permitted.

Account creation is a reconciled multi-service operation: a checked preparation reserves a normalized username and stable internal email derived from request UUID, managed Auth creates the identity, and checked finish binds it once to a Staff profile. Passwords are sent only to managed Auth; the preparation records a server-secret HMAC, not raw passwords. Identical retries return the original result; changed payloads conflict.

Definite Auth400/422 rejection with no Auth identity closes the prepared job as failed through service-only fail RPC, retains failure evidence and releases the alias for a corrected NEW request. An uncertain network/503 result stays pending: retain the SAME request ID and inspect the stable-email identity before retrying; never guess successful account creation. Existing or completed identities cannot be marked failed; reconcile them through checked finish with the original Owner/AAL2 and payload hash. An ordinary Owner token cannot invoke service-only failure marking. Tests cover failed/uncertain/no-false-finish handling and actual DB grants/state effects; hosted Auth behavior is not yet verified.

Verified password recovery requires administrator identity checks through controller-approved channels (a username alone is insufficient), a retained minimal approval/reason, managed Auth recovery/reset, and session revocation as appropriate. Keep the Auth ID/profile/transaction links intact. If MFA is lost, use the provider's reviewed factor-recovery procedure with verified authority; do not bypass normal account-administration verification. Never ask users to send passwords/service keys/recovery secrets in chat. Return access only after current profile/MFA/session checks; no Login History/Activity Log UI is added.
